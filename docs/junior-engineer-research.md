# 初级、中级、高级程序员职责与面试问法研究

> 研究日期：2026-11-20  
> 项目：CareerNav / 岗位与面试 Agent  
> 本轮重点：初级程序员，面向刚毕业、实习、校招和 1-3 年起步岗位  
> 说明：这是一份“岗位能力与面试设计”研究，不把职级当成单纯的技术名词数量，也不把某一个公司的职级体系直接套到所有公司。

## 1. 结论先行

### 1.1 初级程序员不是“低配版高级程序员”

初级工程师的核心价值不是设计大型系统，而是在明确的业务边界、接口约定和验收标准下：

1. 理解需求，确认不明确的地方；
2. 完成一个小模块或明确功能；
3. 处理正常流程和基础边界；
4. 写代码、补测试、查日志、定位常见问题；
5. 如实汇报进度、风险和不会的部分；
6. 接受代码评审并按反馈修改。

对刚毕业学生，面试不应主要考“能不能独立设计高并发系统”，而应验证“基础是否真实、项目是否亲自做过、能不能在指导下交付”。

### 1.2 职级差异首先体现在责任范围，而不是框架数量

| 维度 | 初级 | 中级 | 高级 |
|---|---|---|---|
| 任务边界 | 明确的小任务、小模块 | 一个模块或一组相关功能 | 一个系统、领域或跨模块问题 |
| 需求确定性 | 需求由他人拆解，遇到歧义要确认 | 能把需求转成接口、数据模型和任务 | 能处理模糊需求、系统边界和非功能目标 |
| 技术产出 | 正确、可维护的基础实现 | 稳定模块、异常处理、方案取舍 | 可靠性、性能、架构演进、复杂故障 |
| 验证方式 | 单元测试、手工验证、日志、复现步骤 | 测试策略、监控指标、发布验证 | 指标体系、容量评估、故障演练、演进路线 |
| 协作方式 | 汇报、提问、接受评审 | 与产品/测试/上下游协作 | 技术决策、跨团队推动、指导他人 |
| 风险责任 | 低影响范围，风险及时上报 | 对模块质量和交付负责 | 对系统稳定性、长期成本和团队能力负责 |

这不是说初级不能学习架构，而是说：架构知识可以是加分项，不应成为默认淘汰项。

## 2. 初级程序员的职责模型

### 2.1 输入与理解

- 读懂需求、任务说明、接口文档和验收条件；
- 能指出“哪里不确定”，而不是直接猜测；
- 能区分业务要求、技术约束和自己假设；
- 能把一个任务拆成可执行的几个步骤。

面试应该验证的证据：候选人能否用自己的话复述需求，能否说明输入、输出和边界。

### 2.2 实现

- 在已有设计下实现明确功能；
- 遵循项目代码规范、目录约定和提交规范；
- 正确使用已有组件、工具和框架；
- 先保证正常流程可用，再补边界和异常；
- 不把复制来的代码说成自己从零实现。

面试应该验证的证据：候选人能否说清一个真实接口、页面、测试用例或脚本的具体实现。

### 2.3 正确性与测试

- 能考虑空值、重复、越界、异常、超时等基础边界；
- 会写或执行基础单元测试、接口测试、回归测试；
- 能描述预期结果与实际结果的差异；
- 修复后知道如何验证没有引入新问题；
- 不把“本地能跑”等同于“已经可交付”。

面试应该验证的证据：候选人能否给出一个具体的测试输入、预期输出和失败后的处理方式。

### 2.4 调试与排障

- 能读报错、看日志、复现问题；
- 能逐步缩小范围；
- 能区分代码问题、数据问题、配置问题和环境问题；
- 能说明根因、修复和回归验证；
- 不只会“重启、清缓存、再试一次”。

面试应该验证的证据：让候选人讲一个真实 Bug，重点听定位过程，而不是只听“最后修好了”。

### 2.5 协作与沟通

- 及时汇报进度、阻塞和风险；
- 遇到不会的内容会查文档、搜索、提问；
- 能接受代码评审，不防御性地解释；
- 能把技术问题讲给非技术同事听懂；
- 不隐藏失败，不把团队成果全部归为个人成果。

面试应该验证的证据：项目里“你负责什么、别人负责什么、你如何确认接口、遇到分歧怎么推进”。

### 2.6 学习与边界意识

- 知道自己的知识边界；
- 能在有限时间找到可用资料或求助；
- 不把教程项目包装成生产系统；
- 不把“了解”说成“精通”；
- 能在反馈后调整做法。

## 4. 不同方向：初级岗位的技能与问法

下面的“问法”是面试设计建议，不是招聘公司原话。

### 4.1 Java 后端

市场高频：Java、Spring、MySQL、SQL、MyBatis、Redis、Linux、Git、微服务。

初级应该问：

- 你负责的接口从 Controller 到数据库的完整链路是什么？
- 接口的输入、输出、异常返回分别是什么？
- 如果参数为空、重复提交、数据不存在，会发生什么？
- 你用了哪些表？为什么这样设计？有没有索引？
- 你如何验证接口真的可用？测试了什么边界？
- 你遇到的一个 Bug 是怎么定位的？
- 你在项目中具体做了哪一部分，哪部分不是你做的？

可以问但应控制深度：事务、缓存一致性、JVM、并发、微服务。重点不是背定义，而是能否结合项目说明使用场景和边界。

### 4.2 前端

市场高频：JavaScript、Vue、CSS、HTML、React、TypeScript、Git。

初级应该问：

- 你负责哪个页面或组件？数据从哪里来，状态怎么变化？
- 接口失败、加载中、空数据时页面怎么显示？
- 你如何调试样式、接口或浏览器兼容问题？
- 你如何验证交互和移动端显示？
- 你做过的性能优化是什么，怎么测量前后差异？

不应默认追问大型前端架构、微前端治理，除非候选人项目或岗位明确要求。

### 4.3 测试

市场高频：Python、Java、Linux、SQL、Selenium、自动化、CI/CD。

初级应该问：

- 给你一个功能，你如何设计正常、边界、异常用例？
- 一个 Bug 如何从发现到复现、提交、回归？
- 你如何判断是产品问题、数据问题还是环境问题？
- 你写过什么自动化脚本？失败时怎么定位？
- 你如何证明测试覆盖了关键风险？

### 4.4 运维 / DevOps

市场高频：Linux、Shell、Python、Docker、Kubernetes、MySQL、CI/CD、Nginx。

初级应该问：

- 你如何部署一个服务，失败后如何回滚？
- 服务起不来时，你按什么顺序看日志、端口、配置和依赖？
- 你写过什么脚本，解决了什么重复工作？
- 监控指标异常时，你如何判断影响范围？
- 你有没有在测试环境做过变更验证？

高可用、容量规划可以作为了解项，不应默认要求应届生独立负责。

### 4.5 数据 / AI

市场高频：Python、SQL、数据分析、PyTorch、深度学习、Pandas、机器学习。

初级应该问：

- 你的数据从哪里来，如何清洗和校验？
- 指标如何定义，口径是否一致？
- 你如何划分训练/验证/测试集？
- 模型效果不好时，你如何分析是数据、特征还是模型问题？
- 你如何保证实验可复现？
- 你是否能解释模型的局限和不适用的场景？

不应把“调过一个模型”包装成“能独立负责大模型训练平台”。

### 4.6 嵌入式 / C++

市场高频：C++、Linux、Python、Git、Shell。

初级应该问：

- 你负责的模块输入、输出和资源边界是什么？
- 内存、文件句柄、线程等资源如何释放？
- 你如何编译、烧录、复现和定位问题？
- 你如何区分硬件、驱动、系统和应用层问题？
- 你做过哪些边界测试和稳定性验证？

### 4.7 网络安全

市场高频：Python、Linux、Java、SQL、C++、Shell。

初级应该问：

- 你如何确认测试目标和授权范围？
- 你遇到过什么漏洞，如何复现、验证和推动修复？
- 你如何区分误报和真实风险？
- 你如何写清楚修复建议和回归验证？
- 你如何避免在测试中影响真实业务？

不应把“会用工具”直接等同于“具备独立攻防能力”。

### 4.8 Go 后端

市场高频：Go、Redis、MySQL、Linux、分布式、微服务、高并发、Docker、Kafka。

初级应该问：

- 你负责的接口和服务如何启动、调用和记录日志？
- goroutine、channel 在你的项目里解决什么问题？
- 并发出错时你如何复现和定位？
- 你如何验证消息重复、失败和超时场景？

大型分布式系统设计应作为中高级区分项，而不是应届默认门槛。

## 5. 同一知识点，三个等级的问法差异

### 5.1 以“Redis 缓存”为例

- 初级：你缓存了什么数据？为什么缓存？过期时间怎么定？缓存和数据库不一致时，你怎么发现？
- 中级：你如何设计缓存一致性、穿透/击穿/雪崩处理和故障降级？如何验证？
- 高级：多地域、容量、热点、成本和一致性要求下，缓存架构如何演进？失败时业务如何降级？

### 5.2 以“数据库”为例

- 初级：表有哪些字段？SQL 怎么写？为什么加索引？如何测试查询结果？
- 中级：数据模型如何支持扩展？事务边界在哪里？慢查询如何定位和优化？
- 高级：数据增长、分库分表、迁移、双写、一致性和回滚方案是什么？

### 5.3 以“项目经历”为例

- 初级：你具体做了哪一部分？输入输出是什么？怎么验证？遇到什么 Bug？
- 中级：你如何拆模块、定接口、做取舍、处理异常并保证交付？
- 高级：系统边界、非功能目标、复杂故障、跨团队推动和长期演进如何考虑？

## 6. 面试 Agent 的初级出题策略

### 6.1 推荐的问题生成顺序

1. 从简历项目或岗位 JD 取一个具体事实；
2. 先问“你负责什么”，确认个人贡献；
3. 再问输入、输出、数据流或页面状态；
4. 再问一个基础边界或异常；
5. 再问如何测试、如何定位问题；
6. 最后问哪部分不会、如何学习或求助；
7. 不把“不会架构”直接判为低分。

### 6.2 推荐的内部标签

```text
level: 初级
direction: Java后端 / 前端 / 测试 / 运维 / 数据AI / 嵌入式 / 安全 / Go后端
dimension: 个人实现 / 基础正确性 / 边界异常 / 测试验证 / 调试排障 / 协作学习
evidence_source: 简历项目 / 岗位JD / 真实面试模式
```

### 6.3 评分维度建议

初级评分不要只看“答得长不长”或“命中多少技术词”，应至少区分：

| 维度 | 观察点 |
|---|---|
| 个人真实性 | 能否区分自己做的和团队做的 |
| 技术正确性 | 基础概念和实现是否说得通 |
| 边界意识 | 是否考虑空值、异常、失败和重复 |
| 验证能力 | 有没有测试、日志、复现和回归 |
| 调试过程 | 是否能从现象缩小到根因 |
| 沟通与学习 | 是否如实说明不会、如何求助和改进 |

中高级可以增加：模块独立负责、接口与数据设计、方案取舍、性能与可靠性、跨团队影响、技术治理。

## 7. 不建议对初级默认追问的内容

- 大规模高并发系统架构；
- 跨地域容灾和组织级技术治理；
- 从零设计分布式事务；
- 大规模成本优化和容量规划；
- 要求企业保密项目提供源码、ZIP 或内部数据；
- 只因简历出现一个技术名词，就假定候选人“精通”。

这些内容可以作为“了解程度”或“学习潜力”追问，但不应成为应届生的默认淘汰条件。

## 8. 真实面试记录的校准

从用户提供的真实面试记录中可以看到，实习/初级面试常见的主线并不是纯八股，而是：

- Redis 是否只是看过，还是实际用过；
- Spring Boot + MyBatis 的接口流程能否讲清楚；
- Linux、Docker、Git 到底做过什么；
- 项目业务逻辑、个人职责和难点；
- 一个真实 Bug 的定位过程；
- 不会一个冷门框架时如何查文档、看源码、求助；
- 基础 SQL、分页、注入、缓存和微服务概念；
- 能否在面试官追问时承认“不会”并说明边界。

## 10. 对项目的下一步建议

当前面试 Agent 已经有“初级/中级/高级/架构师”的提示词差异，但还主要是软约束，尚未形成独立的初级题库、问题模板和评分标尺。

建议下一阶段只做初级 MVP：

1. 为 8 个方向各建立一组初级问题模板；
2. 每个问题绑定维度标签和个人实现/边界/测试/调试证据；
3. 初级模式禁止默认生成大规模架构题；
4. 在同一道题上实现三档追问深度；
5. 评分优先奖励“真实、具体、可验证”，而不是奖励“技术词越多越好”；
6. 用 20-30 场真实面试记录校准问法，不直接把未经验证的结论写成企业标准。

这个 MVP 完成后，再扩展中级和高级，不会把不同等级的面试做成同一套题换几个词。

## 11. 中国公司补充研究

为了校正 O*NET 与中国招聘市场之间的差异，后续补充了 100 家中国公司的分层研究，覆盖超大型、大型、中大型、中型、小型和微型企业，并使用 2,864 条严格筛选的初级技术岗位做企业规模比较。

详见：

`D:\何处是家乡\new pj\docs\china-100-companies-research.md`

100 家公司明细：

`D:\何处是家乡\new pj\target\china_100_domestic_companies.csv`

核心发现：

- 中国大公司的初级岗位更常出现算法、数据结构、计算机基础和校招/实习入口；
- 中国小公司更常要求全栈、部署、调试和独立完成完整链路；
- 两类公司都重视沟通、团队、学习、测试和排障；
- 因此中国面试 Agent 不能照搬 O*NET 的抽象能力描述，需要同时建模“公司规模 + 岗位方向 + 具体技术栈 + 真实项目证据”。
