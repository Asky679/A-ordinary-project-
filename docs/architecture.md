# 架构设计说明

## 1. 核心目标

平台不是独立的简历评分器，而是围绕“简历诊断”建立职业发展闭环：

```text
简历事实 -> 岗位需求 -> 简历诊断 -> 面试验证 -> 证据回流 -> 重新诊断 -> 学习行动
```

单智能体负责选择工具、串联工具结果，并向用户输出统一建议。

## 2. 分层设计

### 展示层

- 原生单页应用，无前端构建依赖
- REST 接口统一使用 `ApiResponse<T>`
- 页面包含总览、简历、岗位、项目面试助手、简历诊断五个工作区；技能验证面试作为简历诊断内的弹窗工作区存在，不单独占用导航

### 应用层

- `ResumeService`：结构化简历与 JSON 字段转换
- `JobService`：岗位检索、技能标准化、匹配评分
- `InterviewService`：问题生成、回答评分、会话状态推进
- `DiagnosisService`：六维简历诊断与修改建议生成
- `LearningPathService`：技能差距与阶段路线
- `SkillGraphService`：岗位技能图谱与需求热度

### 智能体层

`AgentOrchestrator` 负责工具链选择和编排：

1. `resume.profile`：读取简历事实
2. `job.match`：计算岗位匹配和技能缺口
3. `interview.start`：创建岗位模拟面试
4. `resume.diagnose`：生成六维诊断报告
5. `learning.generate`：生成学习与项目交付路线

若配置了 `OPENAI_API_KEY`，编排器再调用 LangChain4j `ChatLanguageModel` 生成自然语言总结；模型异常时自动回退到确定性总结，不阻断主链路。

### MCP 层

- `McpJobGateway`：作为 MCP Client，向远程端点发送 `tools/call`
- `McpServerController`：作为本地 MCP Server，支持 `initialize`、`tools/list`、`tools/call`
- `JobRefreshService`：按配置周期刷新岗位
- 远程 MCP 不可用时保留本地岗位库，前端不受影响

## 3. 岗位匹配算法

岗位适配度采用“Agent 受限调权 + 确定性规则评分”：

```text
Agent 读取 JD 职责、任职要求、技能和岗位类型
  -> 输出六维受限权重、逐条证据和调权理由
  -> Java 校验权重并归一化
  -> 规则引擎计算六个维度因子
  -> 应用硬性条件上限
  -> 输出岗位适配度、分项贡献和证据
```

Agent 不直接返回分数。六维默认权重由 AHP 层次分析法计算：

- 技能匹配 34
- 岗位方向 22
- 工作经验 16
- 学历背景 10
- 城市偏好 4
- 项目证据 14

AHP 使用 Saaty 1～9 两两比较矩阵，通过幂迭代求主特征向量，并用随机一致性指标 `RI=1.24` 校验六阶矩阵。当前内置初始矩阵的 `λmax≈6.190`、`CI≈0.038`、`CR≈0.031`，满足 `CR<0.1`。

AHP 分两层输出：

1. `GET /api/jobs/weights/ahp`：全局基准权重；
2. `GET /api/jobs/{id}/weights/ahp`：选择具体岗位后，根据岗位标题、技能数量、经验级别、学历要求和工程深度实时调整权重。

岗位条件化 AHP 使用确定性的岗位特征修正向量，例如实习岗位降低经验权重、提高技能和项目证据权重；高级岗位提高经验和证据权重；技能栈较宽、强调高并发或工程落地时提高技能与证据权重。调整后的六维权重使用 6 位小数归一化，`Σw=1.000000`，同时保留整数百分比用于规则计算。

接口返回判断矩阵、调整后的权重、调整原因、主特征值和一致性结果，便于审计。Agent 只能在受限范围内做进一步调整，例如技能 20～50、岗位方向 10～35、经验 0～30、学历 0～20、城市 0～15、项目证据 0～25。若 Agent 不可用、返回缺项或权重非法，系统自动回退到该岗位的 AHP 权重。

硬性条件不会被调权绕过：

- 核心技能覆盖率低于 50%：最高 55 分
- 岗位方向差异较大：最高 45 分
- 工作经验明显不足：最高 45 分
- 学历不满足：最高 55 分
- 城市不匹配：最高 75 分
- 同时出现两项及以上硬性上限：最高 40 分

推荐页和诊断页复用同一个 Agent 结果缓存，保证同一简历、同一岗位在两个页面使用同一套权重和分数。Agent 结果缓存键包含简历版本与岗位内容哈希，简历或 JD 修改后自动失效。

## 3.1 学历真实性指标

学历材料核验结果会持久化到 `education_verifications`，并作为岗位匹配中的独立硬性指标：

- 只要检测到学信网官方二维码并核验通过，就按有效学历计分，不要求简历字段完全一致；
- 未上传、材料无法识别或没有学信网官方二维码时，按不合格学历处理；
- 只要检测到学信网官方二维码，即按合格学历处理，字段差异仅作为提示；
- 核验未通过时学历维度因子为 `0.20`，明确不一致时为 `0`；
- 学历真实性未通过时，岗位适配度最高不超过 55 分；
- 简历诊断中的“教育基础与真实性”维度会同步降分，并生成 P0 级修复建议。

当简历中的姓名、学校、学历、专业或毕业年份发生变化时，旧核验记录自动失效，必须重新上传材料，避免旧报告被复用于新学历信息。

## 3.2 面试驱动的技能验证

选择题测试链路已经删除。用户从简历诊断页发起五轮技能面试，面试 Agent 按以下顺序形成证据：

```text
基础概念 -> 项目实现 -> 故障与边界 -> 方案取舍 -> 结果验证
```

完成后，`InterviewSkillEvidenceService` 根据完整回答转录评估岗位技能，保存到 `interview_sessions.skill_evidence_json`。证据包含技能、0～100 分、能力等级、置信度、是否已验证和最多三条回答依据。

岗位技能匹配与面试诊断分开计算：

- 简历技能清单命中岗位要求时，该技能直接计为满足；全部岗位技能命中时技能因子为 `1.0`；
- 部分命中时按岗位技能覆盖比例计分，未在简历中声明的技能仍列为缺失；
- 面试评分只用于最终简历诊断、能力深度解释和补强建议，不反向否定简历中已声明的技能；
- 面试中已验证且达到 60 分的额外技能，可以补充简历未声明的技能覆盖；
- 面试评分是可解释的求职准备证据，不是官方技能认证。


Agent 可以调整六维权重，但不能改变“简历技能命中即满足”的匹配口径，也不能绕过硬性分数上限。简历诊断会展示每项技能的面试评分、等级、置信度和证据，并针对低分项生成 P0 修复建议。

## 4. 简历诊断模型

简历诊断拆成两个独立分数：

```text
综合竞争力 = 岗位匹配 × 60% + 简历质量 × 40%
```

简历质量维度：

| 维度 | 权重 |
| --- | ---: |
| 内容完整性 | 20% |
| 成果量化 | 20% |
| 技术深度 | 15% |
| 表达与 ATS | 20% |
| 教育基础 | 10% |
| 项目可信度 | 15% |

岗位匹配直接复用岗位雷达的六维算法。系统同时输出综合分、简历质量、岗位匹配、分项贡献、失分原因和 P0/P1/P2 修改建议。简历更新后，旧诊断报告会自动失效。

## 5. 数据持久化

业务数据使用 PostgreSQL 18.6：

- 岗位、简历、面试会话、诊断报告和采集策略
- 复杂项目、技能、报告结构使用 JSON 文本保存
- PostgreSQL 不保存向量，不再依赖 pgvector

岗位向量使用 Qdrant 1.19.2：

- HTTP API：`http://127.0.0.1:6333`
- Collection：`careernav_jobs`
- 向量维度：256
- 距离：Cosine
- 当前索引岗位：4,110

本地 Embedding 服务：

```text
http://127.0.0.1:5001/v1
tfidf-svd-256
```

Spring Boot 通过 Qdrant REST API 创建 collection、批量写入 points、执行向量检索和返回 Qdrant 状态。

## 5.1 面试题向量库

岗位向量解决“招什么”，面试题向量解决“问什么”，两者分属不同集合、不同嵌入空间，互不干扰。

```text
careernav_jobs                    4,110 条   岗位检索（Java LangChain4j / JobVectorSearchService）
careernav_interview_questions     1,508 条   题库检索（Python LangGraph search_interview_questions_qdrant）
```

数据链路：

```text
4 个公开 GitHub 仓库（MIT / Apache-2.0 / CC-BY-4.0 / CC-BY-SA-4.0）
  -> 只镜像 .md/.json 文本（约 6.7 MB，跳过图片）
  -> 按来源解析为统一 JSONL（题干 / 答案 / 阶段 / 技能 / 来源 / 许可证）
  -> 本地 TF-IDF + TruncatedSVD 256 维（端口 5002）
  -> upsert 到 Qdrant，payload 建索引：source / stage / role / kind / lang / difficulty / skills
```

检索时的自主编排：

```text
LLM 判断是否需要外部题库
  -> 组织查询（候选人回答 / 岗位技能）
  -> 5002 生成查询向量
  -> Qdrant Top-K（stage 过滤，Top-1 分数低于 0.35 时自动放宽过滤）
  -> 返回题干 + 参考要点 + sourceUrl + license
  -> LLM 结合简历改写成追问，并写入面试记忆
```

设计取舍：

- **独立集合**：岗位与题库的向量语义完全不同，混在一起会互相污染召回结果。
- **独立嵌入模型**：题库模型在题库语料上重新拟合，短查询（如“缓存雪崩”）命中率显著优于复用岗位模型。
- **模型热重载**：重建索引会改写模型文件，嵌入服务按 mtime 自动重载，避免查询向量与库中向量属于不同向量空间。
- **降级不阻塞**：Qdrant 或嵌入服务不可用时工具返回 `available:false`，Agent 退回内置模板，面试流程继续。
- **署名可追溯**：每条记录携带 `sourceUrl` 与 `license`，检索结果向使用者展示来源。

## 6. 扩展建议

- 使用对象存储保存 PDF/Word 简历并增加文档解析
- 将项目面试助手接入更多语言源码分析与历史问答版本
- 将单智能体拆成可配置工具注册中心
- 为 MCP 增加 Streamable HTTP/SSE 完整传输层
- 接入学校统一认证、多用户隔离与投递进度管理
- 增加诊断报告历史趋势与 ATS 对比实验
